# CGL — Car Import Logistics

Phase 0 foundation: scaffolding, database schema, auth, and the role system.
No marketing or feature screens yet — every route other than **Login** and
**Register** renders a placeholder with its own name.

**Stack:** Vite · React 19 · TypeScript (strict) · React Router · Tailwind v4 ·
shadcn/ui · Supabase (auth + Postgres) · lucide-react

---

## 1. Running the app

```bash
npm install
cp .env.example .env.local   # then fill in the two values
npm run dev                  # http://localhost:5173
```

Get both values from your Supabase project under
**Dashboard → Project Settings → API**:

| Variable                 | Where to find it        |
| ------------------------ | ----------------------- |
| `VITE_SUPABASE_URL`      | Project URL             |
| `VITE_SUPABASE_ANON_KEY` | `anon` / publishable key |

The anon key is **public by design** — it is compiled into the JS bundle and is
meant to be. Row Level Security is what actually protects the data. Never put
the `service_role` key in a `VITE_`-prefixed variable; anything with that prefix
ships to the browser.

Other scripts:

```bash
npm run typecheck   # tsc -b --noEmit
npm run build       # typecheck + production build
npm run lint        # oxlint
```

## 2. Applying the migrations

The SQL lives in `supabase/migrations/`. **Run the files in numeric order** —
each one depends on the one before it:

| Order | File                          | What it does                                     |
| ----- | ----------------------------- | ------------------------------------------------ |
| 1     | `0001_initial_schema.sql`     | Creates all six tables and their indexes         |
| 2     | `0002_is_admin_helper.sql`    | Creates `is_admin()`, used by every policy       |
| 3     | `0003_rls_policies.sql`       | Enables RLS, grants, and all policies            |
| 4     | `0004_handle_new_user.sql`    | Trigger that creates a profile row on signup     |

### Via the Supabase dashboard (simplest)

**SQL Editor → New query** → paste the contents of one file → **Run**. Repeat
for each file, in the order above.

### Via the Supabase CLI

```bash
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

All four files are re-runnable (`create table if not exists`,
`create or replace function`, `drop policy if exists` before each `create
policy`), so re-applying them is safe.

### Verifying the whole thing works

Once the migrations are applied and `.env.local` holds real values:

```bash
npm run verify:phase0
```

This signs up a throwaway user with the anon key and asserts that the profile
trigger fired, that login works, and that the RLS rules actually hold — a user
cannot promote themselves, cannot credit their own balance, cannot set or change
a vehicle's `status`, and cannot write to invoices, transactions, or shipping
rates. It creates one real auth user and prints the SQL to delete it afterwards.

It needs email confirmation switched off (**Authentication → Providers → Email →
"Confirm email"**); with confirmation on, signup returns no session and the
script says so and stops.

### Verifying RLS took effect

```sql
-- Every table below should report rowsecurity = true.
select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
order by tablename;

-- Should list ~20 policies.
select tablename, policyname, cmd
from pg_policies
where schemaname = 'public'
order by tablename, policyname;
```

## 3. Importing the shipping_rates CSV (435 rows)

Your CSV must have exactly these four column headers, in any order:

```csv
state_code,state_name,branch,rate
CA,California,Los Angeles,850
```

`id` is generated by the database — leave it out of the CSV.

### Option A — dashboard import

**Table Editor → `shipping_rates` → Insert → Import data from CSV**, then drop
the file in. Supabase matches headers to columns by name.

### Option B — psql

```bash
psql "$SUPABASE_DB_URL" \
  -c "\copy public.shipping_rates (state_code, state_name, branch, rate) \
      FROM 'shipping_rates.csv' WITH (FORMAT csv, HEADER true)"
```

Confirm the load:

```sql
select count(*) from public.shipping_rates;  -- expect 435
```

Note that `shipping_rates` is **world-readable** (including signed-out
visitors) by design — the rate table drives the public calculator in a later
phase. Only admins can write to it.

## 4. Promoting a user to admin

There is intentionally **no UI for this, and there should only ever be one
admin.** A user cannot promote themselves: the
`profiles_guard_privileged_columns` trigger raises an exception if a non-admin
tries to change `role` (or `balance`), so the change has to be made from the
dashboard, where queries run as `service_role` and bypass RLS.

1. Register the account normally through `/register`.
2. Open **SQL Editor** in the Supabase dashboard.
3. Run, substituting the real email:

```sql
update public.profiles
set role = 'admin'
where id = (
  select id from auth.users where email = 'you@example.com'
);
```

4. Confirm exactly one admin exists:

```sql
select p.id, u.email, p.role
from public.profiles p
join auth.users u on u.id = p.id
where p.role = 'admin';
```

5. Sign out and back in — the provider reloads the profile on sign-in, and the
   **Admin** nav link appears.

## 5. How the authorization model works

Two layers, and only one of them is a security boundary:

- **RLS policies (the real guard).** Every table has RLS enabled. Policies are
  written against `auth.uid()` and `is_admin()`, so they hold no matter what the
  client sends. Notable rules:
  - A user may insert a vehicle for themselves but **only at status
    `'At Auction'`**, and `UPDATE`/`DELETE` on vehicles is admin-only. Together
    these make `status` unwritable by a non-admin through any path.
  - `role` and `balance` on `profiles` are locked by a `BEFORE UPDATE` trigger,
    because a `WITH CHECK` clause cannot see the old row and therefore cannot
    express "this column did not change".
  - `handle_new_user` hard-codes `role = 'user'` and never reads it from signup
    metadata, which is client-controlled.
- **Route guards + nav hiding (convenience only).** `<RequireAuth>` redirects to
  `/login` without a session; `<RequireAdmin>` redirects to `/dashboard` when
  `role !== 'admin'`; the Admin nav link renders only for admins. All of this is
  UX polish — bypassing it in devtools gains an attacker nothing, because the
  database still refuses the query.
